# Appointment and trip notifications

## Current deployment

Both notification channels are explicitly OFF. Twilio campaign review is pending.
The dashboard has independent SMS/email preferences, an SMS consent reference,
appointment message previews, and a connection status banner. Existing jobs
default to no messaging consent. Website inquiries continue to arrive by email;
staff must copy the inquiry and its actual consent record into the tracker.

Scheduled notifications trigger on first scheduling or an appointment-window
change while scheduled. On-the-way notifications use the real `/track#token`
link generated by the trip endpoint, never a guessed URL. Enabling notifications
does not replay old scheduling events. Opt-in confirmations are attempted when
staff records new SMS consent. Incoming website signups do not themselves trigger
an automatic text; FormSubmit is still the inquiry transport.

## Before enabling

1. Confirm the Twilio campaign is approved and the intended SMS number
   **+1 217-776-8663** is attached to the correct registered Messaging Service.
   Do not purchase another number. Verify the current service SID in Twilio.
2. Apply `migrations/0002_notifications.sql` to `switch-fix-jobs`. No customer
   message bodies or tracking tokens are stored in the notification ledger.
3. Create a production Twilio API key. Store `TWILIO_API_KEY` and
   `TWILIO_API_SECRET` as Cloudflare Worker Secrets for `switch-fix`. Never put
   secret values in chat, GitHub, wrangler vars, logs, or client code.
4. Configure `TWILIO_ACCOUNT_SID` and `TWILIO_MESSAGING_SERVICE_SID` as server
   settings. Sending uses the service SID, so verify its sender pool first.
5. For email, onboard the sender domain to Cloudflare Email Sending and verify
   `info@switchfixelectrical.com`. Add the `EMAIL` send_email binding only once
   that service is available. Preserve the existing Namecheap mailbox MX records.
   The adapter uses the current structured Email Sending API, not legacy routing.
   Confirm the project's Wrangler/runtime supports it before adding the binding.
6. Verify Twilio STOP/HELP handling on that service. Perform a controlled test
   with an authorized recipient and recorded opt-in, checking the confirmation,
   scheduling message, complete private tracking link (including #token), email,
   and opt-out. No real provider test has been performed by this implementation.
7. Only after approval, configuration, and a successful controlled test, set
   `TWILIO_CAMPAIGN_APPROVED=true`, `NOTIFICATIONS_TESTED=true`, and independently
   enable `SMS_NOTIFICATIONS_ENABLED` and/or `EMAIL_NOTIFICATIONS_ENABLED`.
   Email also requires `EMAIL_SENDER_VERIFIED=true`.

## Failure and delivery semantics

Ledger insertion happens before a provider call. A unique event/channel key
allows at most one attempt per event. Accepted means the provider accepted the
request; delivery receipts are not yet integrated. A timeout or interruption may
leave an `unknown` or `sending` entry. Do not retry these blindly: check Twilio or
the email provider first. Rejected/unknown messages do not undo job saves or trips.
When disabled, no ledger access or provider request is made.

No public notification-send endpoint is exposed. Staff authentication and same-
origin write checks remain required. The public tracking API excludes customer
contacts, notes, payments, consent references, and notification results.
